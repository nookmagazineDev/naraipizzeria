# ย้าย QC/RD จาก Google Sheets ไป SQL Server

> ⚠️ **สถานะตอนนี้: QC/RD กลับไปใช้ชีทแล้ว** — `usingSql()` ใน `lib/qcrdSource.js` คืน `false`
> เสมอ ไม่ดู env `QCRD_SOURCE` แล้ว ทั้งเมนู · สูตร BOM · วัตถุดิบ · หมวดหมู่เมนู อ่านและเขียน
> ชีทต้นทุนเมนูผ่าน Apps Script ตามเดิม เพราะทางไปถึงฐานต้องผ่านเครื่องออฟฟิศ พอ host-server
> ไม่ได้รัน/เป็นเวอร์ชันเก่า ฝั่งอ่านถอยไปชีทได้แต่ฝั่งเขียนบันทึกไม่ได้เลยทั้งหน้า
> ตาราง `qcrd_*` กับ `/api/qcrd-migrate` ยังอยู่ครบ เนื้อหาข้างล่างคือวิธีเปิดใช้อีกรอบ
> (ต้องแก้ `qcrdSource()` ให้กลับไปอ่าน env ก่อน ไม่งั้นตั้ง `QCRD_SOURCE=sql` ไปก็ไม่มีผล)
>
> **แต่ SQL ยังถูกอัปเดตอยู่** — บันทึกจากหน้า QC/RD แล้วชีทจะถูกดันขึ้น `dbo.stock_item` ให้เอง
> เพื่อให้หน้านับสต๊อกของ Narai-branch เห็นของที่แก้ ดูหัวข้อ **3.5** ด้านล่าง

> **คำตอบสั้น ๆ:** ย้ายได้ และแก้ไขได้ครบทุกอย่างเหมือนทำในชีท
> แต่ตารางที่มีอยู่ตอนนี้ (`dbo.stock_*` ในฐาน `InventoryNarai`) **ยังไม่พอ** —
> ต้องเพิ่ม **3 ตารางใหม่** (เมนู · สูตร BOM · หมวดหมู่เมนู) และ **6 คอลัมน์ใน `dbo.stock_item`**
> ทั้งหมดอยู่ในไฟล์ [`schema-qcrd.sql`](schema-qcrd.sql) รันไฟล์เดียวจบ

ฝั่งสต๊อกย้ายไปแล้ว (ดู `docs/stock-sql-migration.md` ของรีโป Narai-branch) — ไฟล์นี้คือส่วนที่เหลือ
คือฝั่ง QC/RD ที่ยังอ่าน/เขียนชีทต้นทุนเมนู `1v8WRTaUiEqjtRXzX2g2i5Z8p9FAUvQ37gkdZC8TzhWw` อยู่

ฐานข้อมูลอยู่เครื่องเดียวกับ **ตารางงาน (`narai_hr`)** และ **หน้าสแกนหน้า (`ZKBio9`)**
คือ `NARAI-PIZZARIA\SQLEXPRESS` ที่ `inventory.dyndns.tv` ซึ่งตรึง TCP 1433 และเปิดออกเน็ตอยู่แล้ว
(Narai-branch ต่อตรงแบบนี้กับตารางงานมาตลอด) หน้าเว็บจึงไปถึงข้อมูลได้ 2 ทาง:

```
ทางที่ 1 (แนะนำ)  เบราว์เซอร์ -> /api/qcrd, /api/qcrd-save (Vercel) --ต่อ SQL ตรง--> SQL Server
ทางที่ 2          เบราว์เซอร์ -> /api/qcrd, /api/qcrd-save (Vercel) -> host API /qcrd/* -> SQL Server
```

ทางที่ 1 ไม่ต้องรัน host-server ไม่ต้องเปิด tunnel และไม่ต้องมีกุญแจเขียน — ตั้ง env บน Vercel
ชุดเดียวก็ใช้ได้เลย โค้ดเลือกทางให้เอง (ตั้งรหัสฐานข้อมูลไว้ = ใช้ทางที่ 1, ไม่ตั้ง = ถอยไปทางที่ 2)

## 1) ข้อมูล QC/RD มีอะไรบ้าง และตอนนี้ SQL เก็บครบไหม

ชีทต้นทุนเมนูมี 4 แท็บที่หน้าเว็บใช้ เทียบกับตารางที่มีอยู่แล้วใน `InventoryNarai`:

| แท็บในชีท | ใช้ที่หน้าไหน | ตอนนี้มีตารางรองรับไหม | สรุป |
|---|---|---|---|
| `menu` (เมนู + ราคา + ต้นทุน + ปริมาณที่ได้) | QC/RD > เมนู | ❌ ไม่มีเลย | **ต้องสร้าง `qcrd_menu`** |
| `BOM` (สูตรวัตถุดิบต่อเมนู) | QC/RD > เมนู, หน้ายอดใช้วัตถุดิบ | ❌ ไม่มีเลย | **ต้องสร้าง `qcrd_bom`** |
| `menucodegroup` (หมวดหมู่เมนู) | QC/RD > เมนู (dropdown หมวด) | ❌ ไม่มีเลย | **ต้องสร้าง `qcrd_menu_group`** |
| `item` (ทะเบียนวัตถุดิบ) | QC/RD > วัตถุดิบ, หน้านับสต๊อก | ⚠️ มี `stock_item` แล้ว แต่เก็บไม่ครบ | **ต้องเพิ่ม 6 คอลัมน์** |

### `dbo.stock_item` ขาดคอลัมน์อะไรบ้าง

`stock_item` ถูกสร้างตอนย้ายหน้านับสต๊อก โดยเก็บเฉพาะช่องที่หน้านับสต๊อกใช้
ช่องที่หน้า QC/RD **แก้ได้** แต่ยังไม่มีที่เก็บใน SQL คือ:

| คอลัมน์ในชีท `item` | ความหมาย | สถานะใน `stock_item` |
|---|---|---|
| A รหัส | รหัสวัตถุดิบ | ✅ `item_code` (+ `item_key` ที่ตัด 0 นำหน้า) |
| B ชื่อ | ชื่อวัตถุดิบ | ✅ `item_name` |
| C ราคา | ราคาต่อหน่วยซื้อ | ✅ `price` |
| D หน่วย | หน่วยนับ | ✅ `unit` |
| E สถานะ | ใช้งาน/ปิดการใช้งาน | ✅ `status` |
| **F, G, H ไอเทมทดแทน 1–3** | ของแทนเวลาของขาด | ❌ **ต้องเพิ่ม `sub_item1/2/3`** |
| **I ตัวแปลงหน่วย** | หน่วยเล็กต่อ 1 หน่วยซื้อ (เช่น 1000 กรัม/กก.) | ❌ **ต้องเพิ่ม `converter`** |
| J สาขาที่ใช้ | รายชื่อสาขา | ✅ `stock_item_branch` (แยกเป็นแถว) |
| K itemid (POS) | เลขไอเทมฝั่ง POS | ✅ `pos_item_id` |
| L หน่วยเบิก | หน่วยตอนเบิก | ✅ `request_unit` |
| N หมวดสโตร์ | ที่จัดเก็บ | ✅ `store_cat` |
| **O ประเภท** | วัตถุดิบ / แพ็กเกจจิ้ง | ❌ **ต้องเพิ่ม `item_type`** |
| **P ใช้กับ** | ทั้งสอง / ทานที่ร้าน / ห่อกลับบ้าน | ❌ **ต้องเพิ่ม `used_when`** |

> ⚠️ **เจอปัญหาที่ต้องรู้: คอลัมน์ O ของชีทถูกใช้ชนกันอยู่ตอนนี้**
> `scripts/migrate-stock.mjs` (ฝั่งสต๊อก) อ่านคอลัมน์ O เป็น **Plan** (`TRUE`) เก็บลง `stock_item.plan_only`
> แต่ `qcrd-apps-script.gs` (ฝั่ง QC/RD) **เขียนคอลัมน์ O เป็น "ประเภท"** (วัตถุดิบ/แพ็กเกจจิ้ง)
> แปลว่าทุกวันนี้ ใครเขียนทีหลังคนนั้นทับ — ค่าของอีกฝั่งหายไปเงียบ ๆ
> ย้ายขึ้น SQL แล้วปัญหานี้จบ เพราะแยกเป็นคนละคอลัมน์ (`plan_only` กับ `item_type`)
> ส่วนตอนย้ายข้อมูล สคริปต์จะดูค่าที่อยู่ในช่องแล้วลงให้ถูกช่องเอง
> (`TRUE`/`ture` → `plan_only` · `วัตถุดิบ`/`แพ็กเกจจิ้ง` → `item_type`)

### ตารางใหม่ 3 ตาราง

| ตาราง | มาจากแท็บ | เก็บอะไร |
|---|---|---|
| `dbo.qcrd_menu` | `menu` | รหัส/ชื่อเมนู · หมวด · ราคาขาย · ต้นทุนรวมจากสูตร · สถานะ · ปริมาณที่ได้ต่อ 1 สูตร · ลำดับแถวเดิม |
| `dbo.qcrd_bom` | `BOM` | หนึ่งแถว = วัตถุดิบหนึ่งบรรทัดของเมนู: ยอดใช้ · ตัวแปลงหน่วย · ราคา/ต้นทุนของแถว · ที่มาของสูตร (ดึงมาจากเมนูไหน กี่ %) · แท็ก · ธง "ไม่ตัด BOM" |
| `dbo.qcrd_menu_group` | `menucodegroup` | รหัสหมวด + ชื่อหมวด |

ครบทุกช่องที่ชีทมี ยกเว้นคอลัมน์ที่ไม่มีใครอ่านอยู่แล้ว คือ **BOM คอลัมน์ G** (ค่าคงที่ 1)
และ **คอลัมน์ L** (ว่างเปล่า) ส่วน **K กับ M** ในชีทเป็นค่าเดียวกัน (ต้นทุน/หน่วยเล็ก) จึงเก็บช่องเดียว
และ **คอลัมน์ I** (รหัสวัตถุดิบที่ตัด 0 นำหน้า) กลายเป็น `item_key` ซึ่งเป็นคีย์ที่ใช้จับคู่กับ `stock_item`

## 2) แก้ไขได้ครบเหมือนในชีทไหม

ครบ — ทุก action ที่หน้าเว็บเคยยิงไป Apps Script ถูกเขียนใหม่บน SQL แล้วใน
`host-server/qcrd-db.js` ชื่อและ payload เหมือนเดิมทุกช่อง หน้าเว็บจึงไม่ต้องแก้:

| action | ทำอะไร | บน SQL |
|---|---|---|
| `saveMenu` | เพิ่ม/แก้เมนู + แทนที่สูตรทั้งชุด + คิดต้นทุนใหม่ + ไล่อัปเดตเมนูที่ดึงสูตรกันเป็นทอด ๆ | ✅ ครบ (อยู่ใน transaction เดียว) |
| `saveMenuStatus` | เปิด/ปิดใช้งานเมนู | ✅ |
| `saveMenuGroup` | เพิ่ม/เปลี่ยนชื่อหมวดหมู่ | ✅ (รหัสใหม่ = เลขถัดจากรหัสสูงสุด เหมือนเดิม) |
| `saveItem` | แก้วัตถุดิบ (ชื่อ ราคา หน่วย สถานะ ของแทน ตัวแปลง สาขา หมวดสโตร์ ประเภท ใช้กับ) | ✅ + แก้ `itemid`/`หน่วยเบิก` ได้ด้วย (เดิมต้องไปแก้ในชีทเอง) |
| `addItem` | เพิ่มวัตถุดิบใหม่ | ✅ |
| `deleteItem` | ลบวัตถุดิบ | ✅ + บอกกลับมาว่ารหัสนั้นถูกใช้ในสูตรกี่แถว |
| `updateItemUnits` | เติมหน่วยที่วิเคราะห์จากชื่อ (ไม่ทับของเดิม) | ✅ |
| `sortBom` | เรียงแถวในชีทให้สูตรเมนูเดียวกันอยู่ติดกัน | ไม่ต้องใช้แล้ว — SQL เรียงตอนอ่าน (ยัง call ได้ ไม่ error) |

**สิ่งที่เปลี่ยนไปจากชีท (ตั้งใจ)**

1. **ลบวัตถุดิบไม่ต้องใช้เลขแถวอีกแล้ว** — ในชีทต้องส่ง `_row` มาด้วยเพราะรหัสซ้ำกันได้
   ใน SQL คีย์คือ `item_key` รหัสซ้ำจึงเกิดไม่ได้ ส่ง `row` มาก็ไม่เป็นไร (ไม่ได้ใช้)
2. **รหัสวัตถุดิบที่ซ้ำกันในชีทจะยุบเหลือรายการเดียว** (แถวท้ายสุดชนะ)
   → รันสำรวจก่อนย้ายด้วย `node scripts/migrate-qcrd.mjs --inspect` จะบอกว่ามีกี่รหัส
3. **แก้ราคาวัตถุดิบแล้ว ต้นทุนเมนูเก่ายังไม่ขยับ** — เหมือนพฤติกรรมเดิมของ Apps Script ทุกประการ
   (ต้นทุนคิดใหม่ตอนกดบันทึกสูตรเท่านั้น) ถ้าอยากให้คิดใหม่ทั้งระบบเมื่อราคาเปลี่ยน ค่อยทำเป็นงานถัดไป
4. **หน้ายอดใช้วัตถุดิบ (`/api/usage-bom`) อ่านสูตรจาก SQL ด้วย** เมื่อเปิดโหมด SQL
   จึงเห็นสูตรที่แก้ทันที ไม่ต้องรอแคชชีท 10 นาที

## 3) ขั้นตอนติดตั้ง

ทำที่ **เครื่องออฟฟิศ** ง่ายที่สุด (ต่อ `localhost\SQLEXPRESS` ตรง ไม่ต้องออกเน็ต)
แต่รันจากเครื่องอื่นที่มีเน็ตก็ได้ เพราะ SQL Server ตัวนี้เปิดพอร์ต 1433 ออกเน็ตอยู่แล้ว —
ตั้ง `QCRD_DB_HOST=inventory.dyndns.tv` แล้วใช้ login ชุดเดียวกับ `HR_DB_USER`/`HR_DB_PASSWORD`
(เครื่องที่รันต้องเปิด Google Sheets ได้ด้วย เพราะต้องอ่านชีทต้นทาง)

### วิธีที่ 1 — ให้ Vercel ย้ายให้ (ไม่ต้องเปิดเครื่องออฟฟิศเลย)

Vercel เข้าถึงได้ทั้งชีทและ SQL Server อยู่แล้ว จึงสั่งให้มันย้ายเองได้ ผ่าน `/api/qcrd-migrate`

**ตั้ง env บน Vercel ก่อน** (Settings > Environment Variables แล้ว Redeploy):

| ตัวแปร | ค่า |
|---|---|
| `QCRD_MIGRATE_KEY` | สุ่มข้อความยาว ๆ มาสักชุด — ไม่ตั้ง = ปิดทางนี้ไว้ทั้งหมด |
| รหัสฐานข้อมูล | **ปกติไม่ต้องตั้งอะไรเพิ่ม** — ถ้ามี `ZK_DB_USER`/`ZK_DB_PASSWORD` (หน้าสแกนหน้า) หรือ `HR_DB_USER`/`HR_DB_PASSWORD` อยู่แล้ว โค้ดหยิบไปใช้เอง เพราะเป็น SQL Server เครื่องเดียวกัน · จะใช้ login แยกก็ตั้ง `QCRD_DB_USER`/`QCRD_DB_PASSWORD` ทับได้ |

> ⚠️ **login ที่หยิบมาใช้ต้องมีสิทธิ์ในฐาน `InventoryNarai` ด้วย** — `ZK_DB_USER` เดิมมีสิทธิ์แค่ใน `ZKBio9`
> ถ้ายังไม่ได้ให้สิทธิ์ `step=check` จะฟ้องมาตรง ๆ ให้รันส่วนท้ายของ `docs/schema-qcrd.sql`
> (แก้ตัวแปร `@login` ให้ตรงก่อน) ด้วย `sa` ที่เครื่องออฟฟิศครั้งเดียว

**แล้วเปิดลิงก์ทีละบรรทัด** (เปลี่ยน `<โดเมน>` เป็นโดเมนของ Dashboard และ `<KEY>` เป็นค่าที่ตั้งไว้):

```
https://<โดเมน>/api/qcrd-migrate?key=<KEY>&step=check                 ← ดูสถานะ+สิทธิ์ก่อน ไม่แตะข้อมูล
https://<โดเมน>/api/qcrd-migrate?key=<KEY>&step=schema&confirm=1      ← สร้างตาราง/เพิ่มคอลัมน์
https://<โดเมน>/api/qcrd-migrate?key=<KEY>&step=group&confirm=1       ← หมวดหมู่เมนู
https://<โดเมน>/api/qcrd-migrate?key=<KEY>&step=menu&confirm=1        ← เมนู
https://<โดเมน>/api/qcrd-migrate?key=<KEY>&step=bom&confirm=1         ← สูตร BOM
https://<โดเมน>/api/qcrd-migrate?key=<KEY>&step=item&confirm=1        ← วัตถุดิบ
https://<โดเมน>/api/qcrd-migrate?key=<KEY>&step=verify                ← เทียบจำนวนชีท ↔ SQL
```

- **ต่อไม่ติด (ขึ้น `Failed to connect ... in 15000ms`)** → เรียก `&step=probe`
  จะไล่ทดสอบทุกโฮสต์/พอร์ตที่เป็นไปได้ แล้วบอกว่าอันไหนเปิดจริง พร้อมเช็กให้ด้วยว่า host API
  ของเครื่องออฟฟิศออนไลน์อยู่ไหม (`hostApi.ping`) — เจอพอร์ตที่ใช้ได้ค่อยตั้ง `QCRD_DB_HOST`/`QCRD_DB_PORT` ทับ
  ถ้าไม่เจอเลย แปลว่า SQL Server ไม่ได้เปิดออกเน็ต → ใช้ "ทางที่ 2" (ผ่าน host API) และย้ายข้อมูลที่เครื่องออฟฟิศแทน
- `step=check` บอกว่ากำลังใช้รหัสจาก env ตัวไหน (`credentialsFrom`), login ชื่ออะไร,
  สร้างตารางได้ไหม (`canCreateTable`), เขียนได้ไหม (`canWrite`), และมีตารางแล้วหรือยัง — ดูอันนี้ก่อนเสมอ
- **ไม่ใส่ `&confirm=1` = ทดลอง** อ่านชีทแล้วบอกจำนวนแถวเฉย ๆ ไม่เขียนอะไร ลองก่อนได้ทุก step
- ถ้า `canCreateTable` เป็น `false` → ข้าม `step=schema` แล้วให้คนที่มี `sa` รัน `docs/schema-qcrd.sql`
  ที่เครื่องออฟฟิศครั้งเดียวแทน (หรือให้สิทธิ์ `db_ddladmin` กับ login นั้นตามส่วนท้ายของไฟล์นั้น)
- Vercel ตัดที่ 60 วิ ถ้าชุดไหนใหญ่จนไม่จบ จะตอบ `"done": false` พร้อม `nextOffset`
  → เปิดลิงก์เดิมต่อท้ายด้วย `&offset=<เลขนั้น>` จนกว่าจะได้ `"done": true`
- ทุก step รันซ้ำได้ ไม่เกิดข้อมูลซ้ำ
- เสร็จแล้ว **ลบ `QCRD_MIGRATE_KEY` ทิ้ง** เพื่อปิดทางนี้ (เปิดค้างไว้ = ใครเดา key ถูกก็สั่งย้ายทับได้)

จบแล้วค่อยตั้ง `QCRD_SOURCE=sql` ตามหัวข้อ "เปิดใช้จากหน้าเว็บ" ด้านล่าง

### วิธีที่ 1.5 — เครื่องออฟฟิศเป็นตัวกลาง (ใช้เมื่อ SQL ไม่ได้เปิดออกเน็ต)

ถ้า `step=probe` บอกว่าไม่มีพอร์ต SQL ไหนต่อได้จาก Vercel เลย (ซึ่งเป็นค่าที่ควรเป็นในแง่ความปลอดภัย)
ให้ใช้เครื่องออฟฟิศที่รัน `host-server` อยู่แล้วเป็นตัวกลางแทน — ที่เครื่องนั้นรันคำสั่งเดียว:

สคริปต์จะหาโฟลเดอร์ที่รัน API อยู่ (ตัวที่ตอบ `http://localhost:14365/ping`), อัปเดตไฟล์ QC/RD
(`git pull` ถ้าเป็นรีโป ไม่งั้นโหลดไฟล์จาก GitHub มาวาง), แทรก 2 บรรทัดใน `server.js` เพื่อเปิด
`/qcrd/*` (สำรองไฟล์เดิมไว้ก่อน), ตั้ง `QCRD_WRITE_KEY`, รีสตาร์ท แล้วพิมพ์ลิงก์ย้ายข้อมูลออกมาให้

จากนั้นย้ายข้อมูลจากเบราว์เซอร์เครื่องไหนก็ได้ (เครื่องออฟฟิศเป็นคนอ่านชีทและเขียน SQL เอง):

### เปิดใช้จากหน้าเว็บ

#### ทางที่ 1 — ต่อ SQL ตรงจาก Vercel (แนะนำ, ไม่ต้องแตะเครื่องโฮสต์เลย)

ตั้ง environment variable บน Vercel (Settings > Environment Variables) แล้ว Redeploy:

| ตัวแปร | ค่า | หมายเหตุ |
|---|---|---|
| `QCRD_SOURCE` | `sql` | **ตอนนี้ไม่มีผล** — `qcrdSource()` ปักเป็น `sheet` ไว้ในโค้ด |
| `QCRD_DB_USER` / `QCRD_DB_PASSWORD` | login ที่มีสิทธิ์ใน `InventoryNarai` | **ไม่ต้องตั้งถ้ามี `HR_DB_USER`/`HR_DB_PASSWORD` อยู่แล้ว** — ใช้ชุดเดียวกันได้ |
| `QCRD_DB_HOST` | `inventory.dyndns.tv` | ไม่ตั้ง = ใช้ `HR_DB_HOST` หรือค่านี้เป็นค่าเริ่มต้น |
| `QCRD_DB_NAME` | `InventoryNarai` | ไม่ตั้งก็ได้ |

> ⚠️ login ที่ใช้ต้องมีสิทธิ์ใน `InventoryNarai` ด้วย ไม่ใช่แค่ `narai_hr`
> (ถ้าลืม จะต่อติดแต่ query ไม่ผ่าน ขึ้นว่า *is not able to access the database* —
> ส่วนให้สิทธิ์อยู่ท้าย `docs/schema-qcrd.sql`)

> ทางนี้อาศัยว่า SQL Server เปิดพอร์ต 1433 ออกเน็ตอยู่แล้ว (ตารางงานบน Vercel ใช้ทางนี้มาตลอด)
> ถ้าวันหนึ่งปิดพอร์ตนั้น หน้า QC/RD จะสลับไปทางที่ 2 ได้ทันทีโดยแค่เปลี่ยน env ไม่ต้องแก้โค้ด
> และควรจำกัดสิทธิ์ของ login ที่ Vercel ใช้ให้เหลือเท่าที่ต้องใช้จริง (อ่าน/เขียน 2 ฐานนี้ ไม่ต้องเป็น sa)

เช็กว่าใช้ทางไหนอยู่: เปิด `/api/qcrd?sheet=menugroup` แล้วดูค่า `source` กับ `via`
(`"source":"sql","via":"ต่อ SQL ตรง (inventory.dyndns.tv:1433/InventoryNarai)"`)

#### ทางที่ 2 — ผ่าน host API (ใช้เมื่อไม่อยากเปิดพอร์ต SQL ให้ Vercel)

ตั้ง env **บนเครื่องโฮสต์** (ที่รัน `node host-server/server.js`):

```cmd
set QCRD_DB_SERVER=localhost\SQLEXPRESS
set QCRD_DB_NAME=InventoryNarai
set QCRD_DB_USER=...
set QCRD_DB_PASSWORD=...
set QCRD_WRITE_KEY=<สุ่มข้อความยาว ๆ มาสักชุด>
```

แล้วตั้งบน Vercel: `QCRD_SOURCE=sql` · `QCRD_API_BASE=<URL ของ host API>` ·
`QCRD_WRITE_KEY=<ค่าเดียวกับเครื่องโฮสต์>` (ห้ามตั้ง `QCRD_DB_USER/PASSWORD` ไม่งั้นจะไปใช้ทางที่ 1)

> 🔐 `QCRD_WRITE_KEY` ไม่ใช่ของประดับ — host API เปิดออกเน็ตผ่าน tunnel และไม่มีระบบล็อกอิน
> ไม่ตั้ง = ฝั่งเขียนถูกปิดไว้ (อ่านได้อย่างเดียว) ซึ่งเป็นค่าเริ่มต้นที่ปลอดภัยกว่า

เช็กว่าพร้อมไหม: เปิด `http://<host>/qcrd/ping` ต้องได้
`{"status":"success","menus":<จำนวนเมนู>,"writeEnabled":true}`

### กลับไปใช้ชีท

**ตอนนี้อยู่โหมดชีทอยู่แล้ว** (ปักไว้ในโค้ด ดูกล่องเตือนบนสุดของไฟล์นี้) ไม่ต้องแตะ env
โค้ดฝั่งชีทกับ Apps Script อยู่ครบทั้งอ่านและเขียน

ตอนที่เปิดโหมด SQL: ถ้า host API ล่ม **ฝั่งอ่าน** จะถอยไปอ่านชีทให้เองพร้อมขึ้นคำเตือน
ส่วน **ฝั่งเขียน** ไม่ถอย (ตั้งใจ) เพราะถ้าแอบไปเขียนชีทตอน SQL ล่ม ข้อมูลสองที่จะแยกจากกันทันที
— นั่นคือสาเหตุที่ถอยกลับมาใช้ชีท: เครื่องออฟฟิศดับทีไร หน้า QC/RD บันทึกไม่ได้ทั้งหน้า

## 3.5) แก้ที่ชีท แล้วดันขึ้น SQL ให้หน้านับสต๊อกเห็น

หน้า QC/RD แก้ที่ชีทตามเดิม แต่หน้า **นับสต๊อก** ของ
[Narai-branch](https://github.com/nookmagazineDev/Narai-branch) อ่าน `dbo.stock_item` +
`dbo.stock_item_branch` จาก SQL ผ่าน office-server (ดู `office-server/stock.js` → `getStockItems`)
ไม่ได้อ่านชีท ถ้าไม่ดันขึ้นไป วัตถุดิบที่เพิ่ม/แก้/ปิดใช้งานจากหน้า QC/RD จะไม่ไปโผล่ที่สาขาเลย

**ชีทเป็นต้นทาง SQL เป็นสำเนา** — ทิศทางเดียว ไม่ดึงกลับ:

```
หน้า QC/RD --บันทึก--> Apps Script --> ชีทต้นทุนเมนู (ต้นทาง)
                                          |
                        /api/qcrd-save --ดันต่ออัตโนมัติ--> /api/qcrd-sync
                                          |
                       ต่อ SQL ตรงจาก Vercel  หรือ  host API /qcrd/migrate ที่เครื่องออฟฟิศ
                                          |
                          dbo.stock_item / stock_item_branch / qcrd_*
                                          |
                        office-server --> หน้านับสต๊อกของสาขา (Narai-branch)
```

| ทาง | ทำอะไร | เมื่อไหร่ |
|---|---|---|
| **รายรายการ** (อัตโนมัติ) | ส่ง `action`/payload ชุดเดิมให้ฝั่ง SQL ทำตาม — แตะแค่แถวที่แก้ | ทุกครั้งที่บันทึกสำเร็จ |
| **ทั้งชุด** — ปุ่ม *อัพขึ้น SQL* | อ่านชีททั้งใบแล้ว `MERGE` ทุกแถว + เทียบจำนวนแถวชีท ↔ SQL | ไว้ซ่อมตอนสองที่หลุดกัน |
| **ทั้งชุด** — เปิดเอง | `POST /api/qcrd-sync` `{ "steps": "item" }` · `GET /api/qcrd-sync?steps=all&verify=1` | ตั้งค่าครั้งแรก / ตรวจสอบ |

ทางบันทึกปกติใช้แบบ **รายรายการ** เท่านั้น เพราะการอ่านชีททั้งใบ (เมนูห้าพันกว่าแถว) มา `MERGE`
ใหม่ทุกครั้งที่กดบันทึก กินเวลาหลายสิบวินาทีต่อครั้ง ทั้งที่แก้ไปแถวเดียว
ชื่อ `action` กับรูปแบบ payload ตรงกันทั้งฝั่ง Apps Script และฝั่ง SQL อยู่แล้ว จึงส่งชุดเดียวกันได้เลย

ทั้งสองแบบทำซ้ำกี่รอบก็ได้ ข้อมูลไม่ซ้ำ

### เลือกทางไปถึงฐานยังไง (ต่อตรง ↔ host API)

ทั้งการดันรายรายการและปุ่ม *อัพขึ้น SQL* **ลองต่อ SQL ตรงก่อน ต่อไม่ติดถอยไป host API ให้เอง**
(`viaDirectOrHost` ใน `lib/qcrdSource.js` — ชุดเดียวกับที่หน้าปิดรอบเดือนใช้)

จำเป็นเพราะบน Vercel ตั้ง `QCRD_DB_USER`/`QCRD_DB_PASSWORD` ไว้ใช้กับหน้าอื่น (แพลนสั่งของ · สาขา · RCP)
แต่ไฟร์วอลล์ที่ร้านเปิดให้เฉพาะ IP ในไทย Vercel จึงต่อตรงไม่ได้ ถ้าเลือกทางจาก "ตั้งรหัสฐานไว้ไหม"
อย่างเดียว ปุ่ม *อัพขึ้น SQL* จะขึ้น

> ต่อ SQL Server (inventory.dyndns.tv:1433/InventoryNarai (ใช้ QCRD_DB_USER)) ไม่ได้:
> Failed to connect to inventory.dyndns.tv:1433 in 15000ms

ทั้งที่ทาง host API ใช้ได้อยู่ กติกาของตัวถอย:

* ถอยเฉพาะ error ที่แปลว่า **ไปไม่ถึงเครื่อง** (`Failed to connect` · `ETIMEOUT` · `ECONNREFUSED` · `ENOTFOUND` …)
  ส่วนตารางไม่มี / ไม่มีสิทธิ์ / ข้อมูลไม่ถูก เด้งขึ้นไปให้คนแก้ตามเดิม ไม่กลบด้วยการถอย
* ต่อตรงไม่ติดครั้งหนึ่ง **จำไว้ 5 นาที** แล้วข้ามไป host API เลย (`lib/directRoute.js`)
  จะได้ไม่เสียเวลารอ timeout 15 วิทุกคำขอ — วันไหนเปิดพอร์ตจริงจะกลับไปใช้ทางเร็วเองโดยไม่ต้อง deploy ใหม่
* พังทั้งสองทาง = ข้อความบอกทั้งคู่ (ต่อตรงพังเพราะอะไร · host API พังเพราะอะไร) จะได้ไม่ไล่ผิดจุด
* ผลที่คืนกลับมามีฟิลด์ `route` บอกว่ารอบนั้นไปทางไหนจริง

### ต้องตั้งอะไร

* `QCRD_WRITE_KEY` บน Vercel ให้ตรงกับเครื่องออฟฟิศ (ใช้ทาง host API) **หรือ**
  `QCRD_DB_USER` / `QCRD_DB_PASSWORD` (ให้ Vercel ต่อ SQL ตรง — ตอนนี้ไฟร์วอลล์เปิดให้เฉพาะ IP ในไทย จึงยังไม่ได้)
  ตั้งไว้ทั้งคู่ก็ได้ ต่อตรงไม่ติดจะถอยไป host API ให้เอง (ดูหัวข้อบน)
* host-server ที่เครื่องออฟฟิศต้องเป็นเวอร์ชันที่มี `/qcrd/*` แล้ว — ถ้ายังตอบ HTTP 404
  ให้ `git pull` แล้ว `start-narai.ps1 -Restart` ที่เครื่องนั้นครั้งเดียว
* ปิดการดันอัตโนมัติ (ถ้าอยากกดเอง): ตั้ง `QCRD_SYNC_ON_SAVE=off` บน Vercel

### ข้อจำกัดที่ต้องรู้

| เรื่อง | เป็นยังไง |
|---|---|
| ลบแถว | ลบจากหน้า QC/RD → ตามขึ้นไปด้วย (ดันรายรายการเรียก `deleteItem` ฝั่ง SQL ซึ่งลบแถวจริง) **แต่** ถ้าไปลบในชีทตรง ๆ แล้วมากดปุ่ม *อัพขึ้น SQL* จะไม่ลบให้ เพราะแบบทั้งชุดใช้ `MERGE` — กรณีนั้นให้ตั้งสถานะเป็น "ปิดการใช้งาน" แทน |
| ทิศทางเดียว | แก้ที่ SQL ตรง ๆ จะถูกทับรอบถัดไปที่ดันจากชีท — แก้ที่ชีทเสมอ |
| เครื่องออฟฟิศดับ | บันทึกลงชีทยังสำเร็จ แต่ toast จะขึ้น "⚠ ยังไม่ขึ้น SQL" — เครื่องกลับมาแล้วกดปุ่ม **อัพขึ้น SQL** ทีเดียวจบ |
